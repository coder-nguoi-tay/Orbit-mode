# Multi-Account Manager & Usage-Aware Handoff

## Objective

Let a user run local Codex sessions under distinct, explicitly selected profiles, see each profile's authentication and usage state, and confirm a safe handoff when a profile reaches an authoritative usage limit. Accounts are separate from providers. Orbit never rotates accounts automatically or combines their quotas.

## Current architecture and integration points

- `tauri/src/services/session_manager.rs` creates and resumes sessions through `ProviderRegistry`; the provider owns CLI spawning. `tauri/src/services/spawn_manager.rs::spawn_codex` is the local Codex process boundary.
- `tauri/src/models.rs::Session` and `ui/lib/stores/sessions.ts::Session` have a provider but no account binding. Existing session rows must retain a nullable binding and remain usable.
- `tauri/src/services/database.rs` owns SQLite setup and migrations. `provider_quota_snapshots.account_key` already exists, but `session_manager.rs` records Codex quota events with `account_key = "default"`. The frontend usage store also replaces quotas by provider alone.
- `tauri/src/commands/providers.rs` discovers Codex models via `codex debug models` and otherwise reads the global `~/.codex/models_cache.json`. Target-account compatibility must use the target profile and must not accept a global fallback as proof of access.
- `ui/components/NewSessionModal.svelte` creates sessions; `ui/components/SettingsModal.svelte` is the settings entry; `ui/lib/notifications.ts` already deduplicates desktop attention notices.
- Orbit already has AES-GCM encrypted session/provider API keys in SQLite. This feature must add no credential material to account records or logs. Existing secret storage is a separate migration concern.

## Domain and persistence

- `ProviderAccount`: stable opaque ID, provider ID, user label, auth type (`ChatGPTAuthenticated`, `ApiKey`, `ManagedWorkspace`), execution scope (`Local` or SSH host reference), credential reference/profile home, account status, timestamps, and optional safe identity metadata. Status is an enum: `Available`, `Busy`, `NearLimit`, `QuotaExceeded`, `AuthExpired`, `NeedsLogin`, `Unavailable`, `Unknown`.
- `provider_accounts` stores metadata only. The managed profile path is generated by the backend from the opaque account ID, not from a user label. A special `System Default` account references the existing Codex home without copying or moving it.
- `project_provider_accounts(project_id, provider_id, account_id)` stores overrides. Provider defaults are stored separately. Resolution order is explicit session account, project default, provider default; failure of a bound account is visible and never causes silent replacement.
- `sessions.provider_account_id` is nullable for existing sessions. Newly created local Codex sessions resolve and persist an account before spawn. Preserve the binding through restarts. SSH accounts refer to remote credentials and never receive a local `CODEX_HOME`.
- Add `provider_account_id` to session usage and quota snapshots, while preserving historical rows with unknown/default attribution. Account-level quota samples are never summed by session. Record a non-sensitive session account transition history and audit event.
- Migration must be idempotent and must never modify `~/.codex`, delete credentials, or rewrite existing worktrees/sessions.

## Authentication and isolation

- Use the installed Codex executable for login, status, model discovery, and agent spawn. This installation currently reports `codex-cli 0.157.0`, with `codex login`, `codex login status`, `codex logout`, and `codex debug models`.
- New local Codex profiles use a backend-generated directory under the OS application-data directory, with Unix permissions `0700`. All Codex child commands for that profile receive `CODEX_HOME` in their own process environment. Do not set a global environment variable.
- To guarantee that separate homes also separate credential stores, configure the Codex CLI's supported file credential store for these isolated profiles. The CLI owns `auth.json`; Orbit neither copies nor parses it. A managed policy that overrides this setting must fail profile-isolation verification rather than silently sharing a keyring entry.
- ChatGPT login starts `codex login` in the profile environment and requires the user's browser/device-code completion. `codex login status` verifies the selected authentication method before the account becomes available. API-key login passes the key to `codex login --with-api-key` through child stdin only; it is never inserted into SQLite, command arguments, logs, events, or UI state after submission. If this cannot be made safe on a platform, disable API account creation there with a clear explanation.
- `System Default` uses the pre-existing Codex login without copying credentials. Removing an account unbinds defaults, retains sessions/projects/worktrees, warns about active sessions, and deletes a managed profile directory only through a separate explicit choice after validating its canonical path is inside Orbit's profile root and is not a symlink.

## Session and handoff behavior

- The account selector lists compatible configured profiles. One eligible profile can be preselected; with multiple profiles, show the project/provider default. A remote session can select only a compatible remote account.
- Spawn validates account existence, execution scope, authentication and requested model/effort. It binds the session to that account and injects the profile environment into the Codex child process. Existing Codex conversation IDs are resumed only with the same account.
- Distinguish authoritative plan/weekly/credit exhaustion from transient 429, network, model, and auth errors. A usage estimate may warn but cannot pause a session or mark it exhausted. On authoritative quota exhaustion, retain the worktree and session record, stop only the affected provider process safely, set `needs_account_action`, and show available compatible choices. No account is selected automatically.
- A handoff requires a confirmation dialog naming source account, target account, model, branch, and worktree. The backend serializes handoffs per session, validates the target and model/effort, creates a local context packet from the original task, useful stored messages, Git status/diff, commands/tests, and remaining work, and starts a new provider conversation. It must not assume cross-account conversation IDs are portable.
- Commit the new session account binding and transition audit only after the new process is confirmed healthy. On failure, keep the original binding or record `handoff_failed`; retain worktree, branch and terminal state. Cancellation leaves the session paused. Resume after official reset requires user action unless a separate same-account opt-in policy is enabled.
- Quota events are keyed by account ID and source. Notify on status transitions, not on every sample. Keep pre- and post-handoff usage and cost attributed to the account that actually ran each process.

## UI

- Settings → Accounts supports add, login/status check, rename, defaults, remove, and account detail. Show authentication mode, status, local/remote scope, session count, quota provenance and reset time. Never display or export a secret.
- Agent cards and project dashboards show the bound account label. The Usage Control Center groups provider → account → session, with separate ChatGPT allowance and API usage/billing metrics.
- A quota action panel offers Wait, choose a compatible configured profile, and manage account. The handoff confirmation summarizes Git changes and the target process boundary. Account history remains visible in session detail.

## Acceptance criteria

- Two separately authenticated local Codex profiles can coexist, start agents in the same or different projects, and survive an Orbit restart without credential sharing.
- Session account, per-account quota, per-session usage attribution, authentication status, reset time and dependent agents are visible.
- An authoritative exhausted signal pauses only sessions using that account. Another account remains unchanged. A temporary 429 does not trigger handoff.
- Only an explicit confirmed user choice starts a new account process. The same worktree and branch remain; history and attribution are preserved; failed handoff loses no work.
- No new account secret is stored in Orbit SQLite, logs or UI. No automatic account rotation, quota pooling, or hidden fallback exists.

## Known compatibility constraints

- Codex authentication status reports the authentication method, not a reliable user identity; labels are user-defined.
- Account-specific model discovery is required before handoff. A fallback model list is advisory only, never proof that the target account has access.
- Other providers and remote SSH accounts need provider-specific authentication mechanisms; the initial isolated-login implementation targets local Codex while preserving the account model for them.

## User-approved automatic handoff amendment (2026-09-26)

The product requirement was later expanded to allow an explicit checkbox per local Codex profile. Checked profiles form an automatic handoff pool. After an authoritative quota exhaustion, Orbit may start a new process on the next checked, authenticated profile without opening a confirmation dialog. Each checked profile is used at most once per session, usage history remains keyed by account, and no quota percentages are merged. If the pool has no compatible available profile, the original manual handoff flow remains available.
